== 학습 목표

이 모듈을 마칠 때쯤 여러분은 다음을 수행할 수 있게 됩니다:

* 공식 Helm 차트를 사용하여 OpenShift에 HashiCorp Vault를 배포합니다
* Vault policy, Kubernetes authentication 및 KV secret을 구성합니다
* Vault Agent Injector를 통해 Vault secret을 사용하는 pod를 배포합니다
* External Secrets Operator를 배포하여 Vault에서 secret을 가져와 Kubernetes Secret에 주입합니다

== 왜 Kubernetes에서 Vault를 사용해야 할까요?

HashiCorp Vault는 secret, 인증서 및 암호화 키에 대한 액세스를 저장하고 중개합니다. 컨테이너 이미지, Git 리포지토리 또는 수명이 긴 Kubernetes `Secret` 오브젝트에 자격 증명을 포함하는 대신, Vault는 민감한 데이터를 전용 secrets store에 보관하고 필요에 따라 수명이 짧은 액세스 권한을 발급합니다. 공식 https://github.com/hashicorp/vault-helm[Vault Helm chart]는 Kubernetes 또는 OpenShift에 Vault를 설치하며, 선택적으로 pod secret 주입을 위한 Vault Agent Injector를 배포할 수 있습니다. 이 injector는 어드미션 타임(admission time)에 pod 사양을 변형하여, 애플리케이션이 시작되기 전에 init container가 Vault에 인증하고 secret을 볼륨에 렌더링할 수 있도록 합니다. 

본 실습은 Validated Patterns Framework를 기반으로 구축된 Red Hat 참조 아키텍처인 https://github.com/validatedpatterns/layered-zero-trust[Layered Zero Trust Validated Pattern]의 Layer 1 기능 중 하나를 다룹니다. 해당 패턴은 다음과 같이 레이어별로 컴포넌트를 쌓아 올립니다:

* *Validated Patterns Framework* — OpenShift GitOps (Argo CD) 및 Validated Patterns Operator를 사용하여 클러스터를 부트스트랩합니다. 상위의 모든 것은 Argo CD에 의해 배포되고 조정(reconciled)됩니다.
* *Layer 0 — Foundations* — TLS, compliance scanning, advanced cluster management 및 runtime security enforcement
* *Layer 1 — Feature Sets* — workload identity (SPIFFE/SPIRE), secrets management (Vault + ESO), user authentication (Keycloak), 그리고 선택적으로 private image registry (Quay + NooBaa)
* *Layer 2 — Mapping* — 데모 애플리케이션 (qtodo) 및 선택적으로 secure supply chain pipeline (RHTAS, RHTPA, OpenShift Pipelines)

Vault는 해당 스택의 secrets store 역할을 합니다. 또한 External Secrets Operator (ESO)를 사용하여 표준 secret 참조를 기대하는 workload를 위해 Vault 데이터를 네이티브 Kubernetes `Secret` 오브젝트로 동기화합니다.

[NOTE]
====
본 실습에서는 Vault를 **dev mode**(자동 unseal, root token `root`)로 실행합니다. dev mode는 학습 전용이며, Vault pod가 재시작되면 데이터가 손실됩니다. 프로덕션 환경에서는 dev mode를 사용하지 마십시오.
====

== Vault 배포

워크숍 설치 스크립트는 Agent Injector가 활성화된 HashiCorp Helm 차트를 `vault` namespace에 배포합니다.

.실습 절차
. bastion에서 리포지토리를 클론하고 설치 프로그램을 실행합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
cd ~/
git clone https://github.com/rhpds/openshift-days-ops-showroom.git
cd openshift-days-ops-showroom/setup-scripts/vault-config-scripts
./install-vault.sh
----

스크립트는 다음을 수행합니다:

* HashiCorp Helm 리포지토리를 추가하고 `hashicorp/vault` 차트를 설치합니다
* OpenShift 통합 및 **dev mode**를 활성화합니다
* Vault UI를 위한 OpenShift **Route**를 생성합니다
* pod secret 주입을 위한 **Vault Agent Injector**를 활성화합니다

출력 예시:

[source,bash]
----
[VAULT] Vault URL: https://vault.apps.<cluster-domain>/
[VAULT] Username: Token
[VAULT] Password: root
----

[start=2]
. 스크립트가 완료되면 출력된 URL을 'CTRL + 클릭' 하여 새 탭에서 Vault UI를 엽니다.

[source,bash]
----
https://vault.apps.<cluster-domain>/
----

== Vault 구성

이 단계에서는 Kubernetes 클러스터 내에서 secret을 안전하게 관리하고 액세스할 수 있도록 Vault policy 및 인증 방법을 구성합니다. 이 구성을 통해 승인된 애플리케이션만 Vault에서 민감한 데이터를 검색할 수 있습니다.

먼저 CLI를 사용하여 Vault policy 및 인증 방법을 구성한 다음, UI를 확인하여 구성을 검증합니다. 이 작업은 Vault pod 내부에서 진행됩니다.

.실습 절차
. Vault pod에 연결합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc exec -it -n vault vault-0 -- /bin/sh
export VAULT_ADDR=http://127.0.0.1:8200
export VAULT_TOKEN=root
----

. pod가 secret을 읽을 수 있도록 허용하는 policy 파일을 생성합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
cat <<EOF > /home/vault/read-policy.hcl
path "secret*" {
  capabilities = ["read"]
}
EOF
----

. policy를 적용합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
vault policy write read-policy /home/vault/read-policy.hcl
----
+
. 다음으로, Kubernetes 인증을 활성화합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
vault auth enable kubernetes
----
+
. 그리고 Vault가 service account 토큰을 통해 Kubernetes API 서버와 통신할 수 있도록 허용합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
vault write auth/kubernetes/config \
  token_reviewer_jwt="$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" \
  kubernetes_host="https://kubernetes.default.svc:443" \
  kubernetes_ca_cert=@/var/run/secrets/kubernetes.io/serviceaccount/ca.crt
----
+
. `secret/` 경로에 KV v2 secrets engine을 활성화합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
vault secrets enable -path=secret kv-v2 2>/dev/null || true
----
+
. `vault` namespace의 service account `vault-serviceaccount`에 policy를 바인딩하는 role `vault-role`을 생성합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
AUD=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token | cut -d. -f2 | base64 -d 2>/dev/null | sed -n 's/.*"aud":\["\([^"]*\)".*/\1/p')
vault write auth/kubernetes/role/vault-role \
  bound_service_account_names=vault-serviceaccount \
  bound_service_account_namespaces=vault \
  policies=read-policy \
  ttl=1h \
  audience="${AUD}"
----
+
Vault 1.21은 service account 토큰의 `aud` 클레임을 role `audience`와 대조하여 검증합니다. 위의 명령은 Vault pod 토큰에서 클러스터 audience를 읽습니다(일반적으로 OpenShift에서는 `https://kubernetes.default.svc`임). 
+
. 구성이 완료되면 Vault pod 쉘을 종료합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
exit
----

== Kubernetes Pod에서 Secret 접근

Vault가 구성되고 secret이 저장되었으므로, `vault` namespace에 샘플 애플리케이션을 배포합니다. **Vault Agent Injector**는 pod를 변형하여 Kubernetes 인증으로 인증하고 `/vault/secrets/`에 secret을 렌더링하는 init container를 추가합니다.

deployment는 어노테이션(annotation)을 사용하여 `secret/login` 및 `secret/my-first-secret`을 주입합니다:

* `vault.hashicorp.com/agent-inject: "true"` — 이 pod에 대해 주입을 활성화합니다
* `vault.hashicorp.com/role: "vault-role"` — 사용할 Kubernetes 인증 role
* `vault.hashicorp.com/agent-inject-secret-<name>` — 가져올 Vault 경로
* `vault.hashicorp.com/agent-inject-template-<name>` — 볼륨에 작성될 형식

.실습 절차
. 주입된 secret을 수신하고 OpenShift Route를 통해 노출되는 웹 애플리케이션인 *Vault Secrets App*을 배포합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
cat <<'EOF' | oc apply -f -
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: vault-secrets-app-html
  namespace: vault
  labels:
    app: vault-secrets-app
data:
  index.html: |
    <!DOCTYPE html>
    <html lang="en">
    <head>
      <meta charset="utf-8">
      <title>Vault Secrets App</title>
      <style>
        body { font-family: system-ui, sans-serif; max-width: 40rem; margin: 3rem auto; padding: 0 1rem; color: #151515; }
        h1 { color: #ee0000; }
        code { background: #f0f0f0; padding: 0.1rem 0.3rem; border-radius: 3px; }
      </style>
    </head>
    <body>
      <h1>Vault Secrets App</h1>
      <p>This demo application authenticates to HashiCorp Vault through the <strong>Vault Agent Injector</strong>.</p>
      <p>Injected secrets are mounted at <code>/vault/secrets/</code> inside the pod. Use the lab CLI steps to read them—credentials are not displayed in the browser.</p>
      <p><strong>Status:</strong> Application is running and reachable through the OpenShift Route.</p>
    </body>
    </html>
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: vault-serviceaccount
  namespace: vault
  labels:
    app: vault-secrets-app
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vault-secrets-app
  namespace: vault
  labels:
    app: vault-secrets-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: vault-secrets-app
  template:
    metadata:
      labels:
        app: vault-secrets-app
      annotations:
        vault.hashicorp.com/agent-inject: "true"
        vault.hashicorp.com/agent-inject-status: "update"
        vault.hashicorp.com/role: "vault-role"
        vault.hashicorp.com/agent-inject-address: "http://vault.vault.svc:8200"
        vault.hashicorp.com/agent-inject-containers: "web"
        vault.hashicorp.com/agent-inject-secret-login: "secret/login"

          rhos-token={{ index .Data.data "rhos-token" }}

        vault.hashicorp.com/agent-inject-secret-my-first-secret: "secret/my-first-secret"

          ports:
            - name: http
              containerPort: 8080
          volumeMounts:
            - name: html
              mountPath: /usr/share/nginx/html
              readOnly: true
---
apiVersion: v1
kind: Service
metadata:
  name: vault-secrets-app
  namespace: vault
  labels:
    app: vault-secrets-app
spec:
  selector:
    app: vault-secrets-app
  ports:
    - name: http
      port: 8080
      targetPort: http
---
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: vault-secrets-app
  namespace: vault
  labels:
    app: vault-secrets-app
spec:
  to:
    kind: Service
    name: vault-secrets-app
  port:
    targetPort: http
  tls:
    termination: edge
    insecureEdgeTerminationPolicy: Redirect
EOF
----
+
. pod가 준비될 때까지 대기합니다:

[source,bash,subs="+macros,+attributes",role=execute]

----
+
pod가 `2/2` Ready 상태(web 컨테이너 + Vault Agent 사이드카)가 되면 `Ctrl+C`를 누릅니다.

. 브라우저에서 *Vault Secrets App*을 엽니다 (Windows/Linux에서는 Ctrl+클릭, Mac에서는 Cmd+클릭):

----
+
Vault Secrets App 시작 페이지가 표시되어야 합니다.

. pod에서 주입된 secret을 읽습니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----

예상되는 출력:
+
[source,bash]

+
. 선택 사항: secret이 없는 경우 Agent Injector 로그를 검사합니다:

좋습니다! 첫 번째로 생성한 secret을 실행 중인 pod에 주입했습니다. 다음으로, External Secrets Operator를 사용하여 두 번째로 생성한 secret을 다른 workload에 동기화해 보겠습니다.

== External Secrets Operator를 사용하여 Secret 접근

첫 번째 배포에서는 **Vault Agent Injector**를 사용하여 `/vault/secrets/` 하위에 secret을 파일로 렌더링했습니다. **External Secrets Operator (ESO)**는 다른 패턴을 제공합니다. Vault에서 secret을 읽고 이를 네이티브 Kubernetes `Secret` 오브젝트로 실체화합니다. 그런 다음 workload는 다른 일반적인 Kubernetes secret을 사용하는 것과 동일한 방식으로 `env`, `envFrom` 또는 볼륨 마운트를 통해 해당 secret을 사용합니다.

=== External Secrets Operator 설치

.실습 절차
. 공식 Helm 차트에서 `external-secrets` namespace로 ESO를 설치합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
helm repo add external-secrets https://charts.external-secrets.io
helm repo update external-secrets
helm upgrade --install external-secrets external-secrets/external-secrets \
  -n external-secrets \
  --create-namespace \
  --set installCRDs=true \
  --wait --timeout 10m
----

. 오퍼레이터가 실행 중인지 확인합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get pods -n external-secrets
----

`external-secrets` deployment pod가 `Running` 상태로 표시되어야 합니다.

=== Vault로부터 동기화하도록 ESO 구성

ESO는 Vault UI에서 생성한 `my-second-secret`을 읽고 이를 `my-second-secret-sync`라는 이름의 Kubernetes `Secret`으로 동기화합니다.

dev mode에서 ESO는 Kubernetes `Secret`에 저장된 root 토큰을 사용하여 Vault에 인증합니다. `SecretStore`는 Vault에 도달하는 방법을 정의하고, `ExternalSecret`은 복사할 Vault 경로와 대상 Kubernetes `Secret`의 이름을 정의합니다.

.실습 절차
. `vault` namespace에 토큰, `SecretStore`, 그리고 `ExternalSecret`을 적용합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
cat <<'EOF' | oc apply -f -
---
apiVersion: v1
kind: Secret
metadata:
  name: vault-token
  namespace: vault
type: Opaque
stringData:
  token: root
---
apiVersion: external-secrets.io/v1
kind: SecretStore
metadata:
  name: vault-backend
  namespace: vault
spec:
  provider:
    vault:
      server: "http://vault.vault.svc:8200"
      path: "secret"
      version: "v2"
      auth:
        tokenSecretRef:
          name: vault-token
          key: token
---
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: sync-my-second-secret
  namespace: vault
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: SecretStore
  target:
    name: my-second-secret-sync
    creationPolicy: Owner
  data:
    - secretKey: username
      remoteRef:
        key: my-second-secret
        property: username
    - secretKey: password
      remoteRef:
        key: my-second-secret
        property: password
EOF
----

. ESO가 Kubernetes `Secret`을 생성했는지 확인합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get externalsecret,secretstore -n vault
oc get externalsecret sync-my-second-secret -n vault -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}{"\n"}'
oc get secret my-second-secret-sync -n vault -o jsonpath='{.data.username}{"\n"}' | base64 -d && echo
----

예상 결과: ExternalSecret의 `Ready` 상태가 `True`이고, 디코딩된 username이 `workshop-user-2`여야 합니다.


NOTE: 상태가 `SecretSyncedError`이고 `my-second-secret-sync`가 생성되지 않은 경우, Vault UI에서 `my-second-secret`에 `username`과 `password`가 모두 포함되어 있는지 확인한 후 오류를 조사하십시오:

[source,bash,subs="+macros,+attributes",role=execute]
----
oc describe externalsecret sync-my-second-secret -n vault | tail -20
oc get externalsecret sync-my-second-secret -n vault -w
----

`READY`가 `True`가 되면 `Ctrl+C`를 누른 다음, 위의 검증 명령을 다시 실행합니다.

=== 동기화된 Secret을 사용하는 두 번째 애플리케이션 배포

Vault Agent 파일이 아닌 ESO가 생성한 Kubernetes `Secret`에서 자격 증명을 읽는 두 번째 workload를 배포합니다.

.실습 절차
. 애플리케이션을 배포합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
cat <<'EOF' | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: eso-vault-test
  namespace: vault
  labels:
    app: eso-read-vault-secret
spec:
  replicas: 1
  selector:
    matchLabels:
      app: eso-read-vault-secret
  template:
    metadata:
      labels:
        app: eso-read-vault-secret
    spec:
      containers:
        - name: app
          image: registry.access.redhat.com/ubi9/ubi-minimal:latest
          command: ["sleep", "infinity"]
          env:
            - name: USERNAME
              valueFrom:
                secretKeyRef:
                  name: my-second-secret-sync
                  key: username
            - name: PASSWORD
              valueFrom:
                secretKeyRef:
                  name: my-second-secret-sync
                  key: password
EOF
----

+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get pods -n vault -l app=eso-read-vault-secret -w
----
+
pod가 `1/1` Ready 상태가 되면 `Ctrl+C`를 누릅니다.

[start=2]
. pod가 동기화된 자격 증명을 수신했는지 확인합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
USERNAME_SYNCED=$(oc get secret my-second-secret-sync -n vault -o jsonpath='{.data.username}' | base64 -d)
ESO_POD=$(oc get pod -n vault -l app=eso-read-vault-secret -o jsonpath='{.items[0].metadata.name}')
oc exec -n vault "${ESO_POD}" -c app -- sh -c 'echo "username=${USERNAME}" && echo "password=${PASSWORD}"'
----

예상되는 출력:

[source,bash]
----
username=workshop-user-2
password=workshop-password-2
----

완벽합니다! Vault Agent Injector가 아닌, ESO가 생성한 Kubernetes `Secret`에서 자격 증명을 읽는 두 번째 workload를 배포했습니다. ESO는 workload에서 secret을 사용하는 대체 방법이며 선호하는 secrets store와 함께 사용할 수 있습니다.

== 학습 내용 요약

* **Vault on OpenShift**는 etcd 외부에서 secret을 중앙 집중화하고, **Agent Injector**는 런타임에 이를 pod에 전달합니다.
* **Kubernetes auth**는 Vault 액세스를 특정 namespace 및 service account(`vault-serviceaccount` → role `vault-role`)에 연결합니다.
* **Vault Agent Injector**는 pod 내부의 `/vault/secrets/` 하위 파일에 secret을 작성합니다.
* **External Secrets Operator**는 Vault 데이터를 네이티브 Kubernetes `Secret` 오브젝트로 동기화하여 `env`, `envFrom` 또는 볼륨 마운트와 함께 사용할 수 있도록 합니다.
* Agent Injector (`vault-secrets-app`) 및 ESO 기반의 Kubernetes Secrets (`eso-vault-test`)라는 두 가지 사용 패턴을 배포했습니다.
