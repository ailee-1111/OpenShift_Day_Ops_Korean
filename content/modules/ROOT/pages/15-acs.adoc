== 비보안 애플리케이션 배포

cluster에 취약한 보안 설정을 가진 다수의 애플리케이션을 배포해 보겠습니다. 이를 통해 RHACS의 다양한 보안 기능을 효과적으로 시연할 수 있습니다.

.실습 절차
. 터미널에서 다음 명령을 실행하여 비보안 애플리케이션들을 배포하십시오:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
git clone https://github.com/mfosterrox/demo-applications.git
cd ~/demo-applications
oc apply -f k8s-deployment-manifests/-namespaces --recursive
oc apply -f k8s-deployment-manifests/emojivoto --recursive
oc apply -f k8s-deployment-manifests/apache-struts --recursive
oc apply -f k8s-deployment-manifests/dvwa --recursive
oc apply -f k8s-deployment-manifests/log4shell --recursive
oc apply -f skupper-demo/ --recursive
----
+
애플리케이션들이 배포되는 과정을 확인할 수 있습니다 (출력 생략):
+
----
namespace/emojivoto created
namespace/apache-struts created
namespace/dvwa created
namespace/emojivoto configured
namespace/juice-shop created
namespace/log4shell created
namespace/nodejs-goof-vuln-main created
----

== 보안 및 환경 통찰

**RHACS의 기본 개념을 먼저 살펴보겠습니다.**

=== *RHACS의 기본 기능*
RHACS는 Kubernetes 환경의 필수적인 보안 워크플로우를 위해 다음과 같은 도구를 제공합니다:

- 취약점 관리 (Platform, workloads, Nodes 및 Virtual Machines)
- Policy 수명 주기 관리 (Policy-as-Code)
- Compliance 감사(Compliance auditing)
- 위험 프로파일링(Risk profiling)
- 위협 감지 및 대응(Threat detection and response)

RHACS를 활용하면, CNCF가 지원하는 Kubernetes 환경 전반에서 Kubernetes cluster들을 안전하고 컴플라이언스 규격에 부합하도록 유지할 수 있습니다.

[[rhacs-compliance-operator-installation-and-compliance-checks]]
== Compliance Operator 및 RHACS를 통한 컴플라이언스 점검

프로덕션 cluster와 애플리케이션은 보안 표준 및 내부 policy 규격을 상시 준수해야 합니다. RHACS는 OpenShift compliance operator와 협력하여 보안 상태를 실시간 측정하고, compliance 격차(gap)를 감지하며, 서비스가 프로덕션에 배포되거나 시간이 지남에 따라 compliance에서 이탈(drift)하기 전에 미리 조치할 수 있도록 돕습니다.

먼저, compliance 체크 결과의 차이를 체감할 수 있도록 local cluster에 간단한 configuration을 수정해 보겠습니다.

=== 컴플라이언스 체크 통과를 위한 간단한 클러스터 수정

*ocp4-e8* compliance 표준에 집중하여, `ocp4-e8-ocp-allowed-registries` 통제 항목을 어떻게 패스할 수 있는지 알아보겠습니다. 다음 절차를 실행하여 프로덕션 cluster에 대한 체크를 패스하도록 설정하십시오.

.실습 절차
. 실행하기 위해 아래 명령을 클릭하십시오.
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc apply -f - <<EOF
---
apiVersion: config.openshift.io/v1
kind: Image
metadata:
  name: cluster
spec:
  registrySources:
    allowedRegistries:
      - quay.io
      - registry.redhat.io
      - registry.access.redhat.com
      - image-registry.openshift-image-registry.svc:5000
      - gcr.io
      - docker.io
EOF
----
+
. 변경 사양이 정상 반영되었는지 확인하십시오:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get image.config.openshift.io/cluster -o yaml | grep allowedRegistries -A 10
----
+
**출력 결과**
[source,bash,subs="+macros,+attributes"]
----
    allowedRegistries:
    - quay.io
    - registry.redhat.io
    - registry.access.redhat.com
    - image-registry.openshift-image-registry.svc:5000
    - gcr.io
    - docker.io
status:
  internalRegistryHostname: image-registry.openshift-image-registry.svc:5000
----

좋습니다! 이제 local cluster에 대한 compliance 체크 스캔을 구성해 보겠습니다.

== 런타임 보안 및 불변 워크로드

프로덕션 Kubernetes 환경에서는 cluster 내부에서 실시간 실행되는 대상을 철저히 제어하는 것이 보안상 대단히 중요합니다. 파일 무결성 및 이상 징후 행동을 모니터링하면, 승인된 원래의 이미지나 configuration 규격으로부터 이탈하는 드리프트(drift) 현상을 신속히 감지하는 데 도움이 됩니다.

RHACS는 인가되지 않은 액세스 시도, 지능형 위협(persistent threats), 횡적 이동(lateral movement), 파일 무결성 훼손 등 위험성 높은 비정상 행동을 스스로 감지하고 차단하는 보안 policy들을 내장하고 있습니다. 이 policy들은 컨테이너의 불변성 원칙(immutable container principle), 즉 컨테이너가 뜻하지 않은 불필요한 변경 사항 없이 검증되고 허가된 이미지만 정확하게 실행해야 한다는 규칙을 정밀하게 보장해 줍니다.

== Policy-as-Code를 통한 런타임 비정상 행동 제어

apt, apk, yum, dnf 등의 패키지 관리자(package manager)는 일반 virtual machine 환경에서는 매우 유용하지만, 프로덕션 컨테이너 내부에서 실행되어서는 안 됩니다. 이를 활성화해 두면 임의의 무분별한 소프트웨어 설치를 허용하는 꼴이 되며, cluster 내부의 공격 노출면(attack surface)을 확장하고 프로덕션 workload의 대전제인 감사 가능성(auditability) 및 불변성(immutability)을 정면으로 위배하게 됩니다.

*Policy-as-Code는 다중 cluster 전체에 걸쳐 이러한 보안 보호망을 광범위하게 배포하고 일관되게 규격화하는 매우 탁월한 방법입니다.*

Policy-as-Code 방식을 응용하여 실행(runtime) 중에 감지되는 이상 동작을 실시간 차단하는 보안 구성을 확인해 보겠습니다.

.실습 절차
. *아래의 policy configuration 명령을 터미널에서 실행하십시오*. 이 명령은 컨테이너 구동 중 패키지 관리자의 임의 구동을 탐지 및 차단하는 runtime 보호용 보안 policy를 생성합니다.
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc apply -f - <<EOF
---
apiVersion: config.stackrox.io/v1alpha1
kind: SecurityPolicy
metadata:
  name: alpine-linux-package-manager-execution-patient-portal-enforcement
  namespace: stackrox
spec:
  policyName: Alpine Linux Package Manager Execution - Patient-Portal Enforcement
  description: Alert when the Alpine Linux package manager (apk) is executed at runtime
  rationale: Use of package managers at runtime indicates that new software may be being introduced into containers while they are running.
  remediation: Run 'apk --purge del apk-tools' in the image build for production containers. Change applications to no longer use package managers at runtime, if applicable.
  categories:
    - Anomalous Activity
    - Package Management
  lifecycleStages:
    - RUNTIME
  eventSource: DEPLOYMENT_EVENT
  severity: LOW_SEVERITY
  enforcementActions:
    - FAIL_KUBE_REQUEST_ENFORCEMENT
    - KILL_POD_ENFORCEMENT
  policySections:
    - policyGroups:
        - fieldName: Process Name
          booleanOperator: OR
          values:
            - value: apk
            - value: apk-tools
            - value: apk update
            - value: apk add
            - value: apk remove
            - value: apk upgrade
            - value: apk del
            - value: apk cache
            - value: apk clean
            - value: apk info
            - value: apk show
            - value: apk version
  mitreAttackVectors:
    - tactic: TA0011
      techniques:
        - T1105
  criteriaLocked: false
  mitreVectorsLocked: false
  isDefault: false
EOF
----
+
====
다음 단계에서는 테스트 명령을 구동하는 동시에, OpenShift 이벤트를 관찰하기 위해 `tmux`를 사용할 것입니다. 이를 통해 실시간으로 RHACS가 어떻게 보안 policy를 강제 강행(enforcement)하는지 목격할 수 있습니다.
====
+
. 터미널에서 두 개의 창(pane)으로 나뉜 tmux 세션을 개시하십시오:
+
[source,sh,role=execute]
----
tmux new-session \; split-window -v \; attach
----
+
. 먼저, 첫 번째 shell 창에서 OpenShift 이벤트 스트림을 관찰하는 모니터링 명령을 실행하십시오:
+
[source,sh,role=execute]
----
oc get events -n patient-portal -w
----
+
. *Ctrl+b+o*를 눌러 인접 창으로 제어 포커스를 이동시키십시오.
+
[IMPORTANT]
====
`Ctrl+b`는 tmux 세션을 위한 접두사 단축키(prefix key)입니다. `o`는 인접한 다음 pane으로 화면을 제어 전환하는 작동키입니다.
====
+
. 아래 명령을 활용하여 *patient-frontend* 애플리케이션 pod를 구한 뒤 해당 컨테이너의 내부 shell로 침투(exec)해 보겠습니다.
+
[source,sh,role=execute]
----
POD=$(oc get pod -n patient-portal -l app=frontend -o jsonpath="{.items[0].metadata.name}")
oc exec -n patient-portal $POD -i --tty -- /bin/sh
----
+
.출력 예시
[source,bash]
----
[demo-user@bastion ~]$ POD=$(oc get pod -n patient-portal -l app=frontend -o jsonpath="{.items[0].metadata.name}")
oc exec -n patient-portal $POD -i --tty -- /bin/sh
/home/fritz $
----
+
. 컨테이너 내부 shell 환경에서 아래와 같이 alpine 패키지 관리자 명령을 인위적으로 구동시켜 보십시오:
+
[source,sh,role=execute]
----
apk update
----
+
. 다음과 같이 패키지 관리자가 기동하려고 시도하는 시점에서 아래와 유사한 출력 결과가 생성되는지 관찰하십시오:
+
[source,texinfo,subs="attributes"]
----
/home/fritz $ apk update
ERROR: Unable to lock database: Permission denied
ERROR: Failed to open apk database: Permission denied
/home/fritz $ command terminated with exit code 137
[demo-user@bastion ~]$
----
+
NOTE: *Unable to lock database: Permission denied* 메시지가 나타나는 것은 매우 정상입니다. OpenShift가 pod 보안 규정 덕분에 pod의 root(sudo) 권한 획득 행위를 원천적으로 통제하고 있기 때문입니다.
+
. 아래 하단에 나열되는 oc get events의 tmux 화면을 살피십시오. RHACS가 패키지 관리자의 구동 시도를 즉각 발견하고 해당 pod를 강제로 소멸(delete)시켜 폐기 조치했음을 보여 줍니다:
+
[source,texinfo,subs="attributes"]
----
^C^C[demo-user@bastion ~]$ oc get events -n patient-portal -w
LAST SEEN   TYPE      REASON                 OBJECT                           MESSAGE
50s         Normal    Killing                pod/frontend-8667d5c56b-f9fcj    Stopping container frontend
50s         Normal    Scheduled              pod/frontend-8667d5c56b-s6dph    Successfully assigned patient-portal/frontend-8667d5c56b-s6dph to ip-10-0-61-109.us-east-2.compute.internal
49s         Normal    Created                pod/frontend-8667d5c56b-s6dph    Created container frontend
49s         Normal    Started                pod/frontend-8667d5c56b-s6dph    Started container frontend
50s         Normal    SuccessfulCreate       replicaset/frontend-8667d5c56b   Created pod: frontend-8667d5c56b-s6dph
50s         Warning   StackRox enforcement   deployment/frontend              A pod (frontend-8667d5c56b-f9fcj) violated StackRox policy "Alpine Linux Package Manager Execution - Enforce" and was killed
----
+
[NOTE]
====
수 초 정도 경과하면 해당 위반 pod가 제거되고 새롭게 재생성되는 것을 볼 수 있습니다. 현재 작업 중이던 tmux shell 세션이 강제 종료 처리되면서, 원래 머물던 Bastion VM 커맨드 라인 화면으로 튕겨 돌아오게 됨을 확인할 수 있습니다.
====
+
. tmux 세션을 종료하고 원래의 bastion 호스트 터미널로 완전히 귀환하십시오:
.. 만약 여전히 컨테이너 내부 shell 프롬프트 상에 있다면 `exit`를 입력하여 먼저 빠져나오십시오.
.. tmux 화면에서 실행 중인 `watch` 명령을 중지하기 위해 `Ctrl+C`를 입력하십시오.
.. `exit`를 치거나 `Ctrl-D`를 눌러 tmux 화면 세션을 모두 닫고 bastion 호스트 터미널 화면으로 돌아오십시오.
+
[NOTE]
====
비정상 행동이 사전에 정의한 policy에 의해 실시간 차단 제어되는 것을 확인했습니다. 하지만 이와 같은 시도가 일어났다는 실질적인 위협 정보는 인프라 보안 팀에 신속히 공유되어, 왜 이러한 침투 동작이 유발되었는지 후속 조사(investigate)를 수반해야 합니다.
====

시스템을 파괴할 우려가 있는 자의적인 업데이트 설치 시도를 정상적으로 모니터링하고 성공적으로 차단했습니다! 다만 이제 보안 위협 분석 절차를 위해 반드시 사후 분류 및 심사(triage)가 수반되어야 하는 경고(alert) 로그가 시스템 상에 정식 기록되었습니다.

[[violations-reporting-audit-compliance]]
== 감사 및 컴플라이언스를 위한 위반 사항 분석 및 보고

발생한 이벤트의 감사는 보안 모범 사례를 보장하고, 특정 policy가 트리거되었을 때 있었던 모든 물리적인 기록을 명확히 보존해 줍니다. RHACS는 발생한 위반(violation) 건마다 정교한 포렌식 데이터(forensic detail)를 자동으로 확보하므로, 이를 기반으로 원인을 심도 있게 규명하고 보고서를 생성하며 policy 수준을 더욱 예리하게 가다듬을 수 있습니다.

*실습 절차*

. 웹 브라우저 화면의 RHACS console로 복귀하여, *Violations* 페이지로 이동하십시오.
. policy 위반 항목을 *Policy*, *Name*, `r/alpine` 혹은 가장 최근의 위반 내역으로 정렬 필터링하십시오. policy 통제가 강제 적용(enforced)된 최신 내역을 확인할 수 있습니다.
+
image::acs-security-08.png[RHACS Violations list filtered by policy, link=self, window=blank, width=100%]
+
. 세부 조사 내역을 열어 보기 위해 방금 감지된 *Alpine Linux Package Manager Execution - Patient-Portal Enforcement* 항목을 클릭하십시오.
+
image::acs-security-09.png[RHACS violation detail for package manager policy, link=self, window=blank, width=100%]
+
[IMPORTANT]
====
적절히 구성된 연계 환경 하에서 감지된 개별 violation 로그 내역들은 Security Information and Event Management (SIEM) 솔루션으로 실시간 자동 포워딩되거나 API 조회를 통해 추출할 수 있습니다. UI에 상세히 나열되는 타임스탬프, 구동한 프로세스 유저 ID, 실행 시 입력 인자(arguments), 상위 프로세스 경로(ancestors), 통제 제어 행동(enforcement action) 등의 귀중한 포렌식 자료가 완벽히 보존됩니다.
====
